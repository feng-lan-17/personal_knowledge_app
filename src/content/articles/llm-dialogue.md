这是原创示例教材，不绑定某一家模型或某一个版本。窗口长度、价格和产品名称都会变，下文只保留使用时仍然站得住的结构。

## 一次对话里实际发生的事

你在输入框里写下一段话，按下发送。看起来像是在跟谁交谈。程序这边没有一个藏在后面的人。它做的事情很具体：把你的文字和事先放好的系统说明、之前几轮对话拼成一条上下文，交给模型；模型按自己的参数，估计下一个 token 是什么，写出一个，再把这个 token 接回去，继续估计下一个，直到遇到停止条件。

所以一次对话至少有四段：切分、拼上下文、逐个往下写、停止。后面所有用法，RAG 也好，Agent 也好，都是在这四段的前面或中间插入别的步骤，而不是换掉它们。

## 它不保管你的资料

模型的参数是训练之后固定下来的一大组数字，里面是统计出来的结构，不是一个可以按标题检索的图书馆。它不会因为你昨天在自己的硬盘上存了一份笔记，今天就自动读到那份笔记。你没有放进这次上下文、也没有通过工具真正取回来的内容，它都不该被当成已经查阅过。

把它说成“知道”很容易误导。更稳妥的说法是：在给定上文时，它给下一个 token 分配概率。概率高的续写往往通顺。通顺和属实是两件事。

## Token 是读写单位

模型读写的不是“一个字”或“一个词”的日常概念，而是词表里的 token。英文常常是一个词或半个词；中文可能是一个字，也可能是一个常见词；代码、数字和罕见专名往往被切得很碎。切得碎，同样的字符就会占掉更多位置，费用和窗口都按 token 而不是按你肉眼看到的字数计算。

不同模型的词表不一样。下面只是示意，不是任何一家当前词表的真实输出。

| 文本 | 使用时要单独确认的事 |
| --- | --- |
| 一句中文 | 不能用字数直接换算 token |
| 一段代码或一串编号 | 往往比散文更碎 |
| 很长的材料 | 先问窗口还剩多少，再决定截断、摘要或检索 |

一个常见的查看入口是 OpenAI 的 tokenizer 页面。它只说明那种词表长什么样，不能代表你正在用的另一个模型。

## 上下文窗口是它的全部视野

上下文窗口是这次生成时模型能看见的长度上限。系统提示、历史、你刚贴进来的材料和它已经写出的 token，都挤在同一个窗口里。超过以后，实现通常会截掉前面，或者由外层程序先做摘要。被截掉的部分，这一轮就等于没说。

这也是检索会存在的原因之一：资料库比窗口大。检索不是模型自己打开了你的文件夹，而是别的程序先挑出片段，再把片段放进窗口。

## 提示词是条件，不是咒语

提示词的作用，是在上下文里放条件：角色、材料、输出格式、不许做的事。条件要写得能被检查。“请你更聪明一点”几乎不能检查；“只使用下面材料里的原句，材料里没有的就回答没有”可以检查。

材料如果没放进来，模型仍可能写出像那么回事的话。那不是它查到了，是它在按常见写法续。本库的检索页只做本地全文检索，不把检索结果装成模型的回答。

## 流畅不等于正确

几类限制值得在使用时默认成立，直到你用当前模型和当前材料亲自核对过：

- 算术和精确引用不稳定。看起来整齐的名单、页码、接口名，都要回原处核对。
- 没有工具返回，就没有新的外部事实。
- 很长的上下文里，中间的句子比两头更容易被忽略。
- 训练数据有时间截止，产品若另接了检索，那是产品的能力，不是参数本身突然知道了今天的新闻。

这些边界随版本会有强弱，但“流畅可以与事实分开”这一点不会因为换了一家厂商就消失。

## 下一个词的概率

把上文记成 \(x_{<t}\)，模型给出下一个 token 的分数向量 \(z_t\)，再用 softmax 变成概率：

$$
p(x_t \mid x_{<t})_i = \frac{e^{z_{t,i}}}{\sum_j e^{z_{t,j}}}
$$

温度把 \(z\) 按比例缩放。温度低，高分的 token 更独占；温度高，分布更平，续写更散。贪心解码每次拿当前最高的一个。这些是解码时的选择，不增加模型“知道”的事实。

训练时常见的目标，是让真实的下一个 token 概率变大。写成交叉熵，就是希望模型给那个 token 的 \(-\log p\) 小：

$$
L = -\sum_i y_i \log p_i
$$

这里的 \(y\) 是真实下一个 token 的 one-hot。损失下降只说明预测更接近训练文本的统计，不说明每句回答都已被核实。

## 注意力只先看一眼

生成当前位置时，模型会回头看上文里的各个位置，给它们不同的权重，再按权重把信息加起来。这就是注意力。缩放点积的写法、多头、以及它前面要会的向量和 softmax，放在[从注意力到一次训练](pkl:llm-build)里，避免这一篇同时变成使用说明和推导笔记。

## API 调用时，材料必须真的在消息里

下面是教学用的形状，不是本程序会执行的代码，里面也没有密钥。

```python
# 示例。私人知识图书馆不会运行它，也不保存密钥。
response = client.chat.completions.create(
    model="local-or-official-model",
    messages=[
        {"role": "system", "content": "只根据给定材料回答；材料没有的就说没有。"},
        {"role": "user", "content": materials + "\n\n问题：" + question},
    ],
)
```

如果 `materials` 是空的，系统那句“只根据材料”也没有东西可依。接口换了字段名不改变这一点：没有放进请求里的文章，模型这一次就没看见。

## RAG 是先检索，再放进上下文

检索增强大致是三步。先用问题在资料里找片段，再把片段和问题一起放进窗口，然后才生成。检索错了，生成会顺着错的片段往下说，而且说得很完整。所以要保留来源，并允许回答“材料里没有”。

Lewis 等人在 2020 年的论文里把“先取回文档，再让模型生成”写成了一种用于知识密集任务的结构。产品里的实现细节各不相同，不能把论文里的实验设置当成某个当前接口的说明书。

## Agent 只有在工具真的返回之后才算用过工具

Agent 是在生成循环外面又套了一层循环：模型可以提出调用某个工具，程序真的去执行，把结果写回上下文，模型再继续。没有那一次真实返回，就不应在回答里声称已经查过数据库、已经跑过代码或已经打开了网页。

ReAct 那类工作讨论的是把推理步骤和行动交错起来。它是论文里的一种做法，不是你手头某个产品的菜单说明。

## 怎样阅读一则模型发布

看到一则发布时，可以把它拆开，而不是整段收下：

1. 哪些句子在讲结构，例如上下文、工具、检索。这些可以用上面的框架读。
2. 哪些数字依赖版本，例如窗口多长、价格、榜单分数。这些要写上日期和出处，过期就作废。
3. 哪些是广告口径。本库不收录这类口径，也不编造“最新发布”。

读完可以转到[Token、上下文与提示](pkl:llm-token)，把窗口和提示词再算细一点；若要看权重为什么长成这样，去[从注意力到一次训练](pkl:llm-build)。
